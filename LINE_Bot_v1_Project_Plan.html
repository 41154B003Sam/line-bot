1. 機器人命名與主題 (Topic Title)

正式名稱：智聊小精靈 (Gemini Smart Bot)

命名意涵：以「智慧聊聊」為核心概念，化身為常駐在每位使用者 LINE 聊天室裡的輕巧小精靈。免除複雜 App 下載，透過最熟悉的通訊軟體即可隨時進行繁體中文日常問答、生活規劃與靈感啟發。

2. 目標客群與欲解決問題 (Target Audience & Purpose)

👥 目標客群 (Target Audience)

  • LINE 高頻度日常使用者：上班族、在學學生、自由工作者與家庭生活者。
  • 需要即時靈感與生活解答者：不想打開厚重視窗或搜尋引擎慢慢翻找網頁，希望輸入一句話即可得到精準解答的人群。
  • 追求極簡溝通介面者：習慣手機直覺打字互動，排斥被無關廣告與繁複功能干擾的使用者。

🎯 欲解決之痛點 (Problem Solved)

  • 跨 App 查詢之操作負擔：不再需要切換至外網或付費 AI 平台，在日常聊天室即可 24 小時免費提問。
  • 打破傳統 Bot 死板限制：告別傳統 Echo 機器人只會覆誦或依賴關鍵字匹配的生硬體驗。
  • 手機端排版適配問題：傳統 AI 容易輸出過長字串或在手機上殘留不支援的 Markdown 粗體星號（**），本系統專注於手機閱讀體驗之優化。

3. 本次實作核心功能 (Core Function)

第一版（v1.0）聚焦實作之關鍵核心為：「繁中語意問答與排版收斂引擎」，其包含以下五大核心模組：

模組名稱 技術規格與實作機制
Gemini 模型串接 使用官方 google-genai SDK，注入繁體中文在地化 System Prompt，設定親切幽默之專屬人設。
四重模型自動降級 (Fallback) 依序嘗試 gemini-flash-latest ➜ gemini-3.8-flash ➜ gemini-3.5-flash ➜ gemini-flash-lite，抵禦 503 限流。
輸出長度嚴格控制 限制回覆於 250 ~ 450 字之間（最長不超過 500 字），設定 max_output_tokens=2048 防止 token 不足半句斷頭。
標點安全截斷演算法 若模型偶然超過 500 字，演算法會在倒數最近的標點（。、！、？、換行）安全收尾，絕不留下半句殘詞。
Markdown 星號清洗 自動過濾 LINE 不支援的雙星號 ** 粗體語法，轉為親切自然之條列與 Emoji 排版。

嗨！沒問題，為你精選 3 個搭捷運就能輕鬆抵達的台北一日遊好去處 🚇✨ 1. 中山站赤峰街：漫步文青巷弄小店與老宅咖啡廳，推薦品嚐排隊甜點戚風蛋糕 🍰 2. 大安森林公園站：享受都市森林綠意，野餐放鬆，還能順道漫步永康街吃牛肉麵 🍜 3. 淡水站金色水岸：傍晚漫步淡水河畔看浪漫夕陽，必吃現炸魚酥與阿給小吃 🌅 這條路線交通非常順暢，很適合週末放慢步調散步放鬆喔！祝你有個愉快充實的週末～😊

💻 程式撰寫 (Programming)

  • 捕獲免費版 Gemini 503 尖峰限流並架構 Try-Catch 降級佇列。

📊 簡報產出 (Presentations)

  • 規劃結構完整之 16:9 投影片內容。
  • 編寫現代深色對比卡片視覺 CSS，以無頭瀏覽器產出 PDF。

🌐 網頁與 UX (Web Pages)

  • 產製正式 A4 規格計畫書 HTML 排版。

6. 測試計畫與驗證情境 (Testing Plan)

情境編號 測試情境描繪 輸入操作 預期結果
情境一 正常對話與格式驗證測試 傳送文字：「請用繁體中文解釋什麼是機器學習？」 成功解析 Webhook，產出 250~450 字繁中回答，無 ** 星號，句尾完整以句號結束，手機正常接收。
情境二 貼圖與純 Emoji 過濾測試 聊天室發送貼圖或單一 Emoji「😭」 後台日誌正常記錄 StickerMessageContent，不呼叫 Reply API（已讀不回），節省額度且無報錯。
情境三 尖峰流量模型降級備援測試 模擬主模型 gemini-flash-latest 回傳 503 繁忙 後台自動降級至 gemini-3.8-flash 備援，正常生成文字並回傳，使用者端完全無感。

7. 目前進度、實測結果與未完成部分檢討

7.1 目前進度與實測成果 (Current Progress & Test Results)

  • 端點健康度：本地與 Cloudflare 穿透端點 /health 回傳 HTTP 200 JSON，金鑰布林值正常且無外洩。
  • Webhook 驗證：LINE Developers 後台 Verify 測試通過。
  • 對話實測：手機端文字訊息成功觸發 Gemini 生成，排版符合無粗體星號與字數要求。
  • 極端測試驗證：高頻測試下曾遭遇 Gemini 免費每週配額限制，證實了多模型備援與錯誤訊息回覆機制的健壯性。

7.2 第一版未完成部分與待改善問題 (Unfinished Parts & Improvement Issues)

為追求卓越工程品質，本報告誠實列出 v1.0 尚未涵蓋之項目與下一階段改善規劃：

1. 缺乏多輪上下文記憶 (Stateless)

現狀：目前問答皆為單輪獨立運作，機器人無法記憶上一個問題。例如問「推薦台北景點」，緊接著問「那邊有什麼好吃的？」，Bot 無法將兩者關聯。
改善方向：於 v2.0 引進 Redis 或 SQLite 記錄使用者最近 3~5 輪 Session 歷史。

2. 本地主機依賴與連線中斷風險

現狀：目前依賴本地開發機運行 Flask 與 Cloudflare 臨時隧道，一旦電腦關機或進入休眠，機器人即離線無法回覆。
改善方向：於 v2.0 完成 Docker 容器化封裝，部署至 Google Cloud Run 或 Render 雲端平台。

3. 缺少 LINE 圖文選單 (Rich Menu)

現狀：聊天室底部目前為空白輸入框，缺乏直覺的功能按鈕引導，初次使用者需自行揣摩可發問內容。
改善方向：設計六宮格圖文選單，提供「日常閒聊」、「旅遊推薦」、「工作靈感」等快捷按鈕。

4. 尚未支援多模態圖片識別

現狀：使用者傳送照片時會被忽略，尚未串接 Gemini Vision 進行影像分析。
改善方向：加入 ImageMessageContent 處理器，支援上傳照片進行 OCR 或內容辨識。
